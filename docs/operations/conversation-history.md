# 续聊与历史容量

适用范围：已合入 T-LT-D044 的源码构建。正式项目状态和完整会话记录共用 `workspace.sqlite`；旧安装包仍可能使用 JSON Transcript。工作区主状态的备份、版本兼容和损坏恢复见[工作区恢复说明](./workspace-recovery.md)。

## 各种 Runtime 怎么续聊

| Runtime | 下一轮的历史来源 | 重启后的要求 |
| --- | --- | --- |
| Direct API | 独立保存的完整用户、助手消息 | 开启保存，同一 SQLite 中的完整会话记录可读 |
| Codex | Codex 自己保存的 Thread | 工作区保存 Thread ID，Codex 原生历史仍在；新客户端先恢复 Thread，再发送 Turn |
| Claude Code | Claude 原生 Session / Fork 恢复 | 对应原生历史、认证和 Runtime 可用；本次没有扩大其兼容性声明 |

Codex 恢复拒绝或返回另一 Thread ID 时，应用保留原身份并报错，不会自动创建一个无前文的 Thread。中断请求发送到当前 Thread / Turn；模型停止前应等待完成通知。离线 stdio 回归覆盖调用顺序与 ID，不能替代真实账号和 Runtime 版本验收。恢复顺序依据 [OpenAI App Server 文档](https://learn.chatgpt.com/docs/app-server)。

Direct API 创建分支时，从完整模型消息继承前文；分支拥有独立 Transcript，重启后仍能续聊。Claude 的分支依赖原生恢复，其本地显示记录仍来自近期事件缓存。

## 显示、存档和模型上下文的区别

界面每个会话最多缓存 500 条事件，全局增量事件最多 1,000 条。一段回答可能包含很多 Delta，所以缓存容量不等于消息条数。近期活动、会话内容搜索和部分用量统计仍使用这些缓存，不能当作完整档案或终身统计。Direct API 的模型历史已独立，不受 Delta 淘汰影响，也不再隐式限制为最后 100 条消息。

模型请求仍受上下文容量限制：取模型目录与 Provider 配置的较小容量，扣除输出预算及 128 单位协议空间，再从最新用户消息向前保留连续、完整的问答组。放不下的旧问答仅从本次请求中舍弃，原始存档不删除，也不会自动摘要。如果最新消息单独就放不下，会提示“对话内容超出模型上下文限制”，需要缩短输入或调整有效配置。

估算使用 UTF-8 字节与消息开销，偏保守，不是模型 tokenizer 的精确计数。诊断事件 `context.budget` 记录输入预算、消息保留/舍弃数量和拒绝状态，不记录正文；保存开启时可在 Transcript 中查到。实际 token 用量以 Provider 返回为准。

## 文件与容量

正式数据位于当前 Electron `userData` 目录的 `workspace.sqlite`，使用 WAL 与 FULL 同步。会话按稳定 Session ID 关联；界面事件与完整模型消息共享归档，但模型上下文仍由独立历史接口恢复，不依赖 500 条显示缓存。

| 项目 | 当前规则 |
| --- | --- |
| 默认读写 | SQLite，按会话追加、读取、事务替换 |
| 旧 Transcript | `transcripts/` 中原 JSONL、有效分段和索引仅供首次迁移，保留原字节，不再更新 |
| 初次激活 | 校验全部所需记录、备份、事务导入，保存迁移标记；缺失必需历史时停止激活 |
| 再次启动 | 使用已激活的新库，不用旧文件覆盖新事件或检查点回退结果 |
| 单条事件上限 | 16 MiB，包含 JSON 编码及换行；超限明确提示保存失败 |
| Checkpoint 对话总量 | 8 MiB；这是检查点限制，不是会话归档总量限制 |

旧分段目标 4 MiB、索引上限 1 MiB 的规则继续适用于兼容读取和离线迁移。旧索引指定有效分段；退役段不会重新导入。Checkpoint 仍保存独立的、校验过的对话快照，回退时通过当前 Repository 在事务中替换该会话事件，不改写遗留 JSONL。

当前没有自动磁盘配额或清理。模型消息仍整体保存在内存中，大历史会增加启动时间和内存占用。备份时先退出所有写入者，再复制整个 `userData`；保留数据库与存在的 WAL/SHM、迁移备份及独立检查点，并分别备份项目与原生 Runtime 数据。不要删除新库来强制回退旧 JSON，也不要将目录中所有 JSONL 分段拼接导入。

## 保存与正常退出

从 D052 起，流式事件继续逐条提交到会话存储，模型消息不等待界面缓存或状态合并。高频派生状态使用首个事件起 25 毫秒的合并窗口，不因连续输出一直延后；设置、Provider 配置及关键生命周期仍等待同步提交后确认。

保存失败会显示全局告警，保留已提交的数据和待保存状态；重复失败不持续刷新同一提示。检查磁盘空间、目录权限和备份，再执行明确的保存操作或正常退出以重试。未成功提交的设置/Provider 候选不会在退出时悄悄应用。退出会停止接收新命令，中断并等待当前请求，完成最终状态保存后释放数据所有权。API 请求在 5 秒内仍未确认停止，或最终保存失败时，会提示“退出清理未完成”并以非零状态退出；之后保留完整数据目录再排查。

该合并窗口不是将尚未确认的内存状态声明为已保存。强退、断电或实际磁盘故障仍可能丢失未提交的派生状态；本项目未以异常注入替代硬件断电耐久性验收。相关验证见[状态合并与退出落盘](../spikes/T-LT-D052-coalesced-state-flush.md)。

## 哪些内容不能保证恢复

- 关闭“保存对话”后新增的记录只在当前进程中保留。关闭保存不会删除之前已落盘的内容；再次开启也不会补写关闭期间的内容。若需要重启后有连续历史，建议始终开启保存，或重新开启时新建会话。
- 旧历史迁移时索引损坏或缺少有效分段会停止激活；新库中事件无法解析或保存失败，会标记记录不完整并阻止继续发送及创建分支。先保留整个目录，修复磁盘/权限问题，再恢复完整备份或有效检查点，也可以新建会话。检查点读取本身受损或超过 8 MiB 时也会拒绝操作。
- 已被手动删除、从未保存或因旧版 5 MiB 停写而缺失的内容，无法由升级补回。没有索引且整个 Transcript 丢失时，不能仅凭工作区元数据区分“从未保存”和“被删除”。
- 原生 Runtime 历史不在本地 Transcript 备份中。工作区状态恢复成功不意味着外部 Thread、文件修改及模型上下文回到了同一时间。
