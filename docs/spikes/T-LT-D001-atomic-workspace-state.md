# T-LT-D001：状态文件原子保存

日期：2026-09-21。起点：`d0f6ffe3efd9a4a5881f0e297f7ddfc6a94ac065`。

环境：Windows；Node 24.11.1；pnpm 11.9.0。测试使用临时用户目录，Runtime 发现使用离线替身。

## 问题

`InteractiveWorkspace.#save()` 直接覆盖 `workspace-state-v3.json`。写入中途失败时，原来的完整状态已经被截断，下一次启动无法正常读取。

通过正式 `updateSettings()` 入口注入部分写入失败，旧实现把状态文件留成不完整 JSON。新增回归在修复前为 1 项通过、7 项失败；其中部分写入用例直接证明了原文件被破坏，其余用例检查新增的保存边界。

## 改动

- 状态先序列化，再独占创建同目录的随机临时文件，以 `0o600` 请求创建权限。
- 完整写入后执行 `fsyncSync`，关闭句柄，再用 `renameSync` 替换目标。替换失败时不删除原文件，原始异常继续传给调用方。
- 失败时尝试关闭句柄并清理本次创建的临时文件；清理失败不能覆盖原始保存错误。成功替换后不再执行多余清理。
- 沿用现有文件名和 JSON 结构，不改变读取、迁移及上层业务调用方式。

8 项状态回归均走正式 Workspace 保存入口，覆盖首次创建、连续替换、中文内容与重启读取；临时文件创建失败；部分写入失败；刷盘失败；关闭失败；替换失败；清理失败不掩盖保存错误；替换前进程直接退出。

进程退出测试在独立 Node 子进程中执行真实保存，在替换前以退出码 86 结束进程，不运行清理逻辑。父进程确认旧文件字节未变、仍可恢复，且残留临时文件不会阻止下一次保存。其余文件操作故障通过测试替身注入，正常写入和重启读取使用真实临时目录。

## 范围与结论

T-LT-D001 的验收条件已满足：临时写入或替换失败时，原有效状态仍可读取。

本次保护保存过程；启动时处理已经损坏的文件仍由 D002 负责，备份恢复由 D003 负责。进程退出可能留下临时文件，本次不自动读取或删除这类遗留文件。没有进行断电或网络文件系统验证，也不据此承诺所有文件系统上的断电持久性。
