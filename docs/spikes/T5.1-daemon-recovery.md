## 总结

Desktop 现在支持明确的 `keep` / `stop` Daemon 退出策略。`keep` 会释放 GUI 持有的 stdio 和 IPC 连接，但保留独立 Daemon；新的 GUI Supervisor 从用户数据目录读取原子租约，通过 CurrentUserOnly Named Pipe 的 HMAC challenge-response 再认证，并同时校验 Daemon Instance ID、PID 和协议版本。活租约无法认证时拒绝启动第二个 Daemon；死亡 PID 或无效租约会被清理后再启动。

新增 `@tsukiori/recovery-manager`。它在新 Daemon Boot 中对账活动 ProcessRecord 和非终态 Durable Operation，只依据可观察事实给出 `running`、`committed`、`failed`、`uncertain`、`exited` 或 `orphaned` 结果，自动重放次数固定为 0。所有不确定高风险操作进入 Attention Center 并把 Session 标记为 `recovery_required`。

## T5.1-C1 GUI 退出策略与安全重连

真实进程测试执行以下闭环：

1. Supervisor 启动 Daemon 并发布原子租约；
2. `keep` 策略释放 GUI，Daemon 继续存活；
3. 第二个 Supervisor 使用同一租约完成 challenge-response；
4. 验证 Instance ID 与 PID 未改变；
5. `stop` 策略通过已认证 IPC 请求停止 Daemon；
6. Daemon 退出时只删除属于自身 Instance ID 的租约。

Named Pipe 继续使用 `PipeOptions.CurrentUserOnly` 和客户端 SID 校验。租约只在本机用户数据目录生成，不进入数据库、Fixture、日志或 Git；公开 CI 不需要任何用户凭据。租约的凭据静态保护和 ACL 加固属于 T5.2 的安全发布门槛。

结果：通过。

## T5.1-C2 Durable Operation 恢复结果

Recovery Manager 覆盖：

- Runtime Session Create：外部事实不完整时标记 `uncertain`；
- Worktree Create/Remove：委托 Worktree Fact Reconciler，得到 `committed`、`failed` 或 `uncertain`；
- Commit：不根据 HEAD 猜测归属，要求人工确认；
- Merge/Rebase：保留 Integration Worktree，只允许显式 Continue；
- Cleanup：脏字节或 Git/文件系统事实不一致时保留并标记不确定；
- Stage/Unstage/Revert/Permission Response：均写入可解释恢复结果，不自动执行第二次。

每项结果写回原 Operation，并包含 Daemon Boot ID、恢复时间、原因和 `autoReplay:false`。不确定结果创建稳定 Source Ref 的 `recovery_uncertain` Attention。

结果：通过。

## T5.1-C3 危险操作不自动重放

`RecoveryReport.autoReplayCount` 的类型和值均固定为 0。Prepared 且尚未尝试外部副作用的操作变为 `failed`；Running 操作只有专用 Fact Reconciler 能判定完成，否则保持 `uncertain`。Commit、Merge、Rebase、Revert、Permission Response、Runtime Create 和 Cleanup 不存在自动重放路径。

结果：通过。

## T5.1-C4 PID 复用与完整进程身份

ProcessRecord 对账同时比较：

- PID；
- Daemon Boot ID；
- Process Start Time；
- Spawn Nonce；
- Executable；
- Process Fingerprint。

只有完整身份一致才继续视为运行中。PID 相同但 Start Time 或 Fingerprint 不同会标记 `orphaned`，不会终止观察到的新进程；进程缺失会标记 `exited`；无法观察身份会 fail closed 为 `orphaned/recovery_required`。

结果：通过。

## T5.1-C5 GUI、Daemon、Runtime 强杀矩阵

| 目标 | 故障注入 | 可观察结果 |
| --- | --- | --- |
| GUI Renderer | Electron `forcefullyCrashRenderer()` | 独立 Daemon 和 Runtime 存活，新 UI 可重连 |
| Daemon | G0 实际强杀与 Worktree create/remove crash point | 持久事实可对账，未提交字节保留，危险操作不重放 |
| Runtime | 强杀一个 OpenCode Server / Codex app-server 异常退出 | 对应 Session 可解释为 interrupted/exited，其他 Runtime Handle 保持健康 |

T5.1 新增的 Process 与 Operation 对账覆盖 Daemon 重启后的统一解释；既有真实 Renderer、OpenCode 和 Codex 崩溃测试继续作为回归输入。

结果：通过。

## 失败与修正

第一轮 Recovery 测试把同一 Session 中“一个进程缺失、另一个 PID 已复用”的最终健康状态期望为 `interrupted_daemon`。实现正确选择更保守的 `recovery_required`；测试修正为验证聚合后的最严格状态，没有降低恢复标准。

实现审阅还发现 Daemon Pipe Host error callback 的缩进和测试文件 EOF 格式问题，均在最终验证前修正。
