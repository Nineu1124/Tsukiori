## 结论

T1.2 的四个 Checkpoint 均已完成。Desktop Main 生成仅驻留于父子进程内存/环境块的随机 bootstrap token；Daemon 创建随机名称、`CurrentUserOnly` 的 Windows Named Pipe，并在接受连接后通过客户端 PID 对应的用户 SID 验证 Peer Identity。双方随后校验 `daemonInstanceId`、协议版本、32 字节随机 challenge 和 HMAC-SHA256 proof，认证完成后才开放 JSON-RPC 请求。

GUI 连接以随机 `connectionEpoch` 区分。断线重连会关闭旧 transport、重新完成认证，并使用 `lastStreamSequence` 与 `knownSnapshotVersion` 选择完整 Snapshot 或缺失增量。非法参数、未知方法、超大消息、无效 JSON、不兼容协议、旧 Daemon instance 和错误 proof 均被拒绝；审计只记录固定事件类型、固定原因、脱敏时间和 connection epoch，不记录 token、proof、challenge、SID、参数正文或源码。

## T1.2-C1 当前用户边界与 Peer Identity

实现与证据：

1. 服务端以 `PipeOptions.CurrentUserOnly | Asynchronous | WriteThrough` 创建 Named Pipe，不开放 TCP 监听。
2. 接受连接后调用 `GetNamedPipeClientProcessId` 获得对端 PID。
3. 通过 `OpenProcess`、`OpenProcessToken` 与 `WindowsIdentity` 读取对端用户 SID，并与 Daemon 当前用户 SID 做等值比较。
4. SID 不相同则在认证前断开；通过后只记录 `peer.verified/current_user_sid`，实际 SID 只存在于内存，不写入 Fixture 或仓库。
5. 测试断言 ready envelope 的 ACL 模式为 `current_user_only`，认证响应必须含 `peerIdentityVerified: true`，审计必须出现 Peer 验证记录。

结果：通过。

## T1.2-C2 Daemon 身份、Challenge-response 与协议版本

握手顺序：

1. Desktop Supervisor 每次启动生成 32 字节随机 bootstrap token，通过子进程环境传给 Daemon；用户提供的 environment 不能覆盖它。
2. Daemon 每次启动生成随机 `daemonInstanceId` 和随机 Pipe 名，并等待 Pipe host 就绪后才发送 `daemon.ready`。
3. 每个连接生成独立 32 字节 challenge 和 connection epoch。
4. 客户端计算 `HMAC-SHA256(token, challenge|daemonInstanceId|protocolVersion)`。
5. 服务端依次拒绝不兼容协议、旧 instance 和无效 proof；proof 使用固定时间比较。
6. Supervisor 同时验证 Host Protocol、Daemon Version 与 IPC Protocol，任一不匹配即终止子进程。

自动测试覆盖兼容连接、不兼容 v99、随机旧 instance、随机错误 token；审计中不包含 bootstrap token。Fixture 只保留 `<uuid>` 与 `<random-per-connection>` 占位符。

结果：通过。

## T1.2-C3 Snapshot、增量与重连

服务端订阅接受两个非负整数游标：

- Snapshot version 未知或不一致：返回 Snapshot 和 `lastStreamSequence` 之后的事件。
- Snapshot version 一致：只返回 `lastStreamSequence` 之后的增量。
- 每次连接返回不同 connection epoch；关闭旧客户端后，旧客户端不能再发送请求。

两层测试提供证据：

- 独立真实 Pipe 测试验证首次 `[1,2]`、重连后只返回 `[2]`、epoch 发生变化、旧客户端请求被拒绝、连接关闭被审计。
- `DaemonSupervisor` 生命周期测试通过真实 Daemon 启动链验证首次 Snapshot 与重连增量，而不是只测试孤立的 Pipe Harness。

结果：通过。

## T1.2-C4 输入拒绝与脱敏审计

已验证拒绝：

- `incompatible_protocol`
- `stale_instance`
- `invalid_proof`
- `invalid_params`
- `method_not_found`
- `invalid_json`
- `message_too_large`（实现固定 65,536 字节上限）

JSON-RPC 只允许 `daemon.ping` 与 `stream.subscribe`。订阅参数必须是非负整数。接收缓冲和单消息均有固定上限。客户端还校验 challenge、authenticated envelope、response id 和响应结构；异常 transport 会拒绝全部 pending waiter。

审计采用固定字段 `type/reason/connectionEpoch/at`。`at` 在测试输出中始终替换为 `<timestamp>`；代码不输出请求参数、challenge、proof、token、SID、Prompt 或用户文件内容。

结果：通过。

## 失败注入与修正记录

1. 首次 Daemon 集成编译发现 `stdio: ['ignore','pipe','pipe']` 与 `ChildProcessWithoutNullStreams` 不兼容。改为 `ChildProcess` 并在启动时显式验证 stdout/stderr 句柄。
2. 首次真实启动有 Pipe 创建前连接的 `ENOENT` 竞态。客户端对 `ENOENT/ECONNREFUSED/EPIPE` 进行有界重试；Daemon 仅在服务端 handle 已创建后发 ready。
3. 客户端断开曾使 PowerShell reader/writer dispose 抛 broken-pipe 并退出循环。所有清理均改为捕获并记录固定原因，服务端继续接受下一连接。
4. 扩展 stale-instance 测试时 raw 客户端误发送字面量 `\\n`，服务端正确等待行结束，测试因而超时。修正为真实 newline，并给隔离测试设置 15 秒失败上限。
5. Supervisor 的停止 `Promise.race` 没有取消已输掉的 10 秒 timer，导致测试进程延迟退出。改为 `finally` 清除 timer，并处理已退出子进程，Host suite 从约 12 秒降至约 2 秒。
6. 连接关闭审计断言首次多转义一个反斜杠，实际审计已存在但正则未匹配。修正断言后完整 IPC suite 通过。
