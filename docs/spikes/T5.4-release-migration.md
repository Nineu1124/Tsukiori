## T5.4-C2 Desktop/Daemon 独立版本与协议兼容

Release Manifest 分开记录：

- Desktop version、Host Protocol、IPC Protocol、可接受 Daemon Protocol 范围、最大数据库 Schema；
- Daemon version、Host Protocol 和 IPC Protocol。

测试使用 Desktop `1.0.0-rc.1` 与 Daemon `1.1.0`，证明版本号无需相等；只有 Host Protocol 位于声明范围且 IPC Protocol 相等时才允许更新。现有启动链同时继续检查 `DAEMON_VERSION`、`HOST_PROTOCOL_VERSION` 和 `IPC_PROTOCOL_VERSION`，不兼容 Daemon 不会被复用或重复启动。

结果：通过。

## T5.4-C4 签名与来源验证

Release 验证顺序固定为：Manifest Shape → Desktop/Daemon Protocol → Key ID Allowlist → Ed25519 Signature → HTTPS Origin/Channel → URL 文件名 → Artifact Byte Length/SHA-256 → Database Schema。任一步失败都不会进入安装或回滚。

自动化测试用只存在于进程内的临时 Ed25519 Key 对测试 Artifact/Update Manifest 真实签名，验证正确 Artifact 通过，篡改内容、篡改来源、错误渠道和未知 Key 均失败。私钥没有写入文件、Fixture、日志或仓库。

Windows Publisher 检查只接受 `Get-AuthenticodeSignature` 等价输入中的 `Status=Valid` 且 Thumbprint 位于信任列表。正式构建设置 `TSUKIORI_REQUIRE_CODE_SIGNING=1` 后启用 electron-builder `forceCodeSigning`；本机无发布证书时实测退出码 1，并报告 `App is not signed and forceCodeSigning is set to true`。因此本机未签名 NSIS 只能作为工程测试 Artifact，不能通过 Release Gate。

结果：通过。

## T5.4-C5 回滚与数据库降级阻断

更新或回滚必须携带目标 Desktop 的 `maximumDatabaseSchema`。Release Manager 在 Artifact 真实性和来源验证完成后，比较当前数据库 Schema；当前值更高时返回 `database_downgrade_blocked`。Database 自身也在读取 `schema_migrations` 后拒绝 `highestApplied > targetVersion`，形成更新层与持久层双重保护。

测试把当前 Schema 设置为 7、目标应用最大 Schema 设置为 6，验证回滚拒绝；把 v6 数据库交给 targetVersion 5 的 LocalDatabase，验证同样拒绝。

结果：通过。
