# T2.3 Setup、Cleanup 与 Workspace Binding 实施报告

- 任务：T2.3
- 完成日期：2026-08-02
- 平台：Windows x64
- Workspace Manager：0.1.0
- SQLite Schema：v5

## 结论

T2.3 的四个 Checkpoint 均已实现。新增 `@tsukiori/workspace-manager`，统一负责独立 Worktree 绑定、项目 Setup/Cleanup 动作、动作审计和 Session 归档。默认可写模式只接受 `isolated-worktree`，一个 Session 只能有一个 Workspace Binding；不同 Session 的 Worktree ID、分支和 canonical path 均不同。

结构化 `exec` 始终使用 executable 与参数数组并保持 `shell: false`。原始 Shell 是单独的 action 类型，必须携带 approval source；Windows V1 只允许显式选择 PowerShell 或 cmd。审计不保存 Shell script、命令参数或原始 stdout/stderr，只保存脚本/输出 SHA-256、字节数、退出码和 timeout 状态。

Setup 失败不会触发 Worktree remove：Binding 进入 `setup_failed/retained`，Session 进入 `stopped/error`，脏状态和逐动作诊断仍可读取。归档默认保留 Worktree；无论保留还是显式清理，Binding 都保存 Session、Project、Worktree、base commit、last-known commit 和 cleanup state。

## T2.3-C1 结构化命令与显式授权 Shell

`exec` 调用只接受 executable 和 args 数组；`spawnSync` 固定 `shell: false`。Shell action 必须提供非空 `approvalSource`，并使用明确的 `powershell` 或 `cmd` 类型。`bash`/`zsh` 在 Windows Native V1 被标记为不支持并在启动进程前拒绝。

自动测试分别执行 Node structured exec 和已批准 PowerShell action，验证两类审计字段互斥：exec 记录 executable；Shell 记录 shell type、approval source 和 script hash。持久化审计中不存在 Shell script 与原始输出。

结果：通过。

## T2.3-C2 Setup 失败保留可诊断状态

失败注入先由 Setup action 创建未跟踪代码文件，再由下一 action 以退出码 7 失败。验证结果：

- Worktree 路径和创建的文件仍存在；
- WorktreeRecord 标记为 `dirty`；
- Workspace Binding 标记为 `setup_failed/retained`；
- Session 标记为 `stopped/error`；
- 两条 action audit 可读取，失败动作保存退出码和输出哈希；
- 不存在任何 `worktree_remove` Operation。

结果：通过。

## T2.3-C3 每个可写 Session 独立绑定

两个 `isolated-worktree` Session 使用同一 Project 并分别创建 Workspace。测试验证 Workspace Binding ID、Worktree ID、路径和分支均独立，并且各 Session 的 `primaryWorkspaceBindingId` 指向自己的 Binding。`shared-workdir` 和 `read-only` 不会被可写 Workspace 创建入口隐式升级。

结果：通过。

## T2.3-C4 归档后的可追溯性

归档前以结构化 Git 参数读取 `HEAD^{commit}`。默认归档不删除 Worktree，Binding 进入 `archived/retained`；Session、last-known commit、WorktreeRecord 和真实路径仍可定位。

显式 `cleanup: run` 先运行并审计 Cleanup actions，再调用 T2.2 的非 force Worktree remove。干净 Worktree可进入 `removed/succeeded`；action 失败进入 `failed`，dirty、active process 或其他 T2.2 安全拒绝进入 `blocked`，不会伪装成成功。

结果：通过。

## 失败与修正记录

1. 首次 TypeScript 构建发现 `spawnSync().error` 的静态类型是 `Error`，不能直接读取 `code`；改为显式收窄到 `NodeJS.ErrnoException` 后记录 timeout/error code。
2. 首次接入根 `package.json` 时 PowerShell 精确替换误写了字面量换行标记，pnpm 在执行前即拒绝无效 JSON；随后修复为真实 CRLF 并重新运行安装与测试。
3. Action 输出最初容易被理解为可持久化诊断；最终合同明确为有界内存输出，SQLite 仅保存 SHA-256 与字节数。
4. 首轮 Host 测试发现包边界断言已经增加 `workspaceManager` 变量，但 Promise manifest 列表漏加对应元素，导致位置错配；补入显式 manifest 后重新运行 Host 测试。

## 安全边界

- Worktree 是代码隔离，不是安全沙箱。
- Setup/Cleanup 的批准语义不会代替 Runtime 权限系统；这里只保存批准来源引用。
- 公开 Fixture、CI 和报告不包含用户路径、凭据、原始 Prompt、原始 Runtime 事件或 action 输出。
- Cleanup 默认保留；即使用户显式请求清理，T2.2 的 dirty/untracked/process 保护仍不可绕过。
