# T1.5 Permission Broker、Attention Center 与基础 UI 实施报告

- 任务：T1.5
- 完成日期：2026-08-02

- Permission Broker：0.1.0

## 结论

T1.5 的五个 Checkpoint 均已实现。新增 `@tsukiori/permission-broker`，统一校验 Runtime 权限请求、Connection Epoch、可用决策、持久规则与审计；数据库 v3 新增权限规则、审计和 Attention Inbox。Electron Renderer 提供 Session Timeline、Tool Card、Permission Card 与 Attention Center，通过固定 Preload API 接收只读快照，所有 Runtime 文本只以 `textContent` 写入 DOM。

项目级允许只接受结构化、可验证 matcher，且请求必须可执行拦截；原始 Shell 字符串、`observable_only` 与 `opaque` 请求不能形成广泛项目放行规则。Renderer 崩溃由真实 Electron 进程注入，崩溃后独立 Daemon 和已处于 running 的 Fake Session 均继续存活。

## T1.5-C1 权限信息可观察

Permission Request 标准化为 Permission Card，保留且展示：

- 类别 `category`；
- 风险 `risk`；
- 影响范围 `scope`；
- `Enforcement Level`；
- 标题、说明、可用决策和 Connection Epoch。

真实 Electron smoke 模式通过固定 IPC 注入脱敏权限、Tool 和 Attention 数据，等待 Renderer 完成异步渲染后断言三类卡片各一张，权限类别为 `shell`、Enforcement Level 为 `interceptable`。

结果：通过。

## T1.5-C2 决策、规则与审计

自动化测试分别执行 `allow_once`、`allow_session`、`allow_project`、`deny_once` 和 `deny_session`，五条审计均包含请求、Session、Project、Epoch、类别、风险、Enforcement Level、决策作用域和时间。Session 允许、项目允许和 Session 拒绝生成对应持久规则；一次性决策不生成规则。

安全负例验证：带 `{ raw: ... }` 的 Shell matcher 无法建立项目规则，`observable_only` 或 `opaque` 请求也不能建立项目允许规则。失败不会留下规则或伪造审计成功记录。

结果：通过。

## T1.5-C3 Attention Center

Attention 持久层和 UI 支持：

- `waiting_permission`；
- `waiting_input`；
- `completed`；
- `failed`；
- `conflict`；
- `recovery_uncertain`。

权限请求自动创建等待权限事项，决策后将其解析为 resolved；Runtime 重连使旧 Epoch 请求 invalidated，同时创建 recovery uncertain 事项。Inbox 按开放状态与更新时间读取。

结果：通过。

## T1.5-C4 GUI 重启恢复

测试在同一 SQLite 文件中创建待处理权限和六类 Attention，关闭数据库以模拟 Host/UI 客户端退出，再创建新的 LocalDatabase 和 PermissionBroker 实例。重新读取后仍有一条 pending Permission 和完整 Attention 历史。Renderer 只请求快照，不拥有事实状态，因此 GUI 生命周期不会清除待处理事项。

结果：通过。

## T1.5-C5 Renderer 崩溃隔离

真实 Electron smoke 测试先启动独立 Daemon 和 Fake Runtime Session，使 Fake Session 进入 `running/healthy`；待卡片渲染完成后调用 `forcefullyCrashRenderer()`。随后验证：

- Renderer gone reason 为 `crashed`；
- Daemon 仍为 running 且可以响应版本探测；
- Fake Session 仍为 `running/healthy`；
- Fake Runtime 已接收的事件仍保留。

结果：通过。

## 失败与修正记录

1. 增强 smoke 测试首次在 `did-finish-load` 后立即读取 DOM，发现 Renderer 的顶层异步 IPC 尚未完成，卡片数为 0。探测改为最多 2 秒的有界 UI-ready 轮询，再进行崩溃注入；修正后稳定通过。
2. `apply_patch` 在当前 Windows restricted-token sandbox 无法准备可写根，文件变更改用精确锚点与 UTF-8 无 BOM 写入，并由 `git diff --check`、TypeScript 和全套测试验证。

## 后续边界

- T1.5 只提供本地 Broker、持久化和基础只读 Snapshot UI；真实 Codex/OpenCode 权限透传分别属于 T3.3、T4.2。
- Permission Broker 只能治理 Runtime 实际上报或 Host 可拦截的请求，不声称拦截 opaque 行为。
- Renderer 按钮尚不直接拥有 Runtime 能力；后续命令必须经固定 IPC、Broker 重新校验和当前 Epoch 验证。
- 生产 Daemon 的常驻恢复、资源配额和诊断包属于 T5。
