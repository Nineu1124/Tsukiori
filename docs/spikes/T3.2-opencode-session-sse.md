T3.2 的四个 Checkpoint 已由正式 Bridge、脱敏 Global SSE Fixture、集成测试和真实 Runtime 启动探针覆盖。每个 OpenCode Runtime Handle 固定只有一个 global SSE 读取器；所有 Session 事件由该读取器按 Runtime Session ID 路由到 Host Session/Turn；Runtime Scope 事件独立保留。SSE 断开后，恢复流程重新 Probe Runtime、切换并持久化新 Connection Epoch、读取 Session Snapshot、写入恢复警告与 Session 状态，再建立新的单一读取器。

## Checkpoint 证据

### T3.2-C1 Create、Resume Session 与 Start Turn

- `createSession` 先验证 Provider/Model 已连接，再创建 OpenCode Session，并将 Runtime Session ID 绑定到 Host Session。
- `resumeSession` 使用 `session.get` 验证持久 Runtime Session，拒绝 ID 不一致或 Profile 不匹配。
- `startTurn` 在调用 `promptAsync` 前创建 Host Turn 和活动路由，因此同步到达的早期 SSE 不会丢失。
- Host Turn 只保存 `{ source: "opencode", persistedText: false }`；用户输入文本不写入 SQLite、Fixture、报告或日志。
- 测试覆盖 SSE 早于 HTTP 204 返回的竞态；终态一旦完成，不会被较晚的 running 写回覆盖。
- 结果：通过。

### T3.2-C2 文本、工具、权限、完成和错误映射

| OpenCode Native Event | Host Event |
| --- | --- |
| `message.updated`（assistant start/finish） | `assistant.message_started` / `assistant.message_completed` |
| `message.part.delta` | `assistant.text_delta` |
| `message.part.updated`（tool state） | `tool.started` / `tool.progress` / `tool.completed` / `tool.failed` |
| `permission.asked/replied` | `permission.requested` / `permission.resolved` |
| `question.asked/replied/rejected` | `user_input.requested` / `user_input.resolved` |
| `session.idle` | `turn.state_changed`（completed） |
| `session.error` | `turn.state_changed`（failed）或 Runtime error |

- Event Envelope 由公共 `EventNormalizer` 生成，包含 Runtime Handle、Host Session/Turn、流序号、Session 序号与 Connection Epoch。
- 只投影路由和状态所需字段；工具输入/输出、权限 metadata、完整错误消息及未知事件原始 payload 不落入 Fixture。
- 独立失败注入证明 `session.error` 将 Turn 标为 failed、Session Health 标为 error，且脱敏错误文本未持久化。
- 结果：通过。

### T3.2-C3 多 Session 单读取器与 Runtime Scope

- `OpenCodeSessionBridge.eventReaderCount` 固定为 1；Create/Resume 不创建额外 SSE 消费者。
- 两个 Host Session 并行创建和启动 Turn，均观察到各自的文本、工具、权限与完成事件，且 Session/Turn ID 不交叉。
- 未带 Session ID 的 `server.connected` 等事件以 Runtime Scope 保存，不会因 Session 路由缺失而丢弃。
- Session 创建事件可能早于 HTTP 响应；Bridge 每个 Runtime Session 最多缓冲 64 个早期事件，绑定后按到达顺序归一化。
- 结果：通过。

### T3.2-C4 断线、重新 Probe、Snapshot 与新 Epoch

- Fake Runtime 首个 Global SSE 连接被主动断开，Bridge 可观察为 `disconnected`。
- `recoverEventStream` 调用 Runtime `reProbe`，拒绝不兼容版本，然后生成不同于旧值的新 Connection Epoch。
- 新 Epoch 同时更新 Bridge、`runtime_handles` SQLite 记录和后续 Event Envelope。
- 恢复读取 `global.health`、`session.status` 和每个已绑定 `session.get`；无法确认的 Session 标为 `recovery_required`，不伪装健康。
- 因 OpenCode 1.18.4 的 Global SSE 不承诺历史重放，恢复明确写入 `runtime.warning`（`event_replay_unavailable`）和 Snapshot Session 状态。
- 恢复完成后仍只有一个 global SSE 读取器。
- 结果：通过。

## 失败与修正记录

1. 首轮恢复测试发现 `LocalDatabase.saveRuntimeHandle` 的 upsert 没有更新 `connection_epoch`。内存已切换新 Epoch，但 SQLite 仍是旧值。已将 `connectionEpoch` 加入冲突更新字段，并由断线集成测试与数据库测试回归。
2. Fake Runtime 可在 `promptAsync` 的 HTTP 204 返回前同步发送完成事件。Bridge 增加终态保护，避免较晚的 running 状态覆盖 completed/failed。
3. Global SSE 断开时没有历史 replay token。恢复策略不猜测遗漏事件，而是新 Epoch + `runtime.warning` + Snapshot。
4. 未绑定 Session 的早期事件不能直接归入 Runtime Scope，否则会破坏路由；改为有界缓冲，绑定后再处理。

## 安全边界

- API Key、Server 密码、认证文件、完整用户输入、模型完整输出、用户源码和原始 Native Event 不进入公开证据。
- 固定 Preload/Renderer 边界不因 SSE 增加新的直接网络入口。
- SSE、工具、权限、问题、错误和未知事件全部按不可信数据处理。
- Global SSE 的 Runtime Scope 是事件路由范围，不代表 OS 安全隔离；Worktree 仍不是安全沙箱。
