# T4.3 Codex 原生能力展示实施报告

- 任务：T4.3
- 完成日期：2026-08-02
- 平台：Windows x64
- Codex Adapter：0.1.0
- 锁定协议版本：0.146.0
- 实际 Probe：本机 Codex 0.146.0，无模型 Turn

## 结论

T4.3 的四个 Checkpoint 均已实现。Codex Adapter 新增只读 Native Capability Probe，通过 app-server 读取有效配置摘要、MCP 状态摘要、Skills 清单摘要、Windows Sandbox readiness 和 T4.1 已有认证投影。Renderer 在 Runtime 专属面板中显示每项能力的 SupportLevel、EnforcementLevel、native scope 和脱敏摘要。

Probe 不保存完整 config、配置层路径、Skill 名称/描述/正文/路径、MCP server 名称/URL、工具 Schema 或认证材料。所有能力明确标记为 `runtime_native`；不存在 common capability 输出。Sandbox 的 readiness 为 `ready` 只证明 readiness 接口成功，不证明某个 Turn 已被 OS Sandbox 实际约束，因此 EnforcementLevel 继续为 `unknown`，UI 明示 `enforcement=unknown`。

## 官方基线

本任务按 2026-08-02 刷新的官方 Codex 手册与版本化 Schema 实现：

- [Codex App Server](https://learn.chatgpt.com/docs/app-server.md)：富客户端通过 app-server 获得认证、会话、审批和原生事件；stdio 使用 JSONL。
- [Sandbox](https://learn.chatgpt.com/docs/sandboxing.md)：Sandbox 和 Approval 是不同控制；Sandbox 定义技术边界，Approval 决定越界时是否暂停。
- [Windows sandbox](https://learn.chatgpt.com/docs/windows/windows-sandbox.md)：Windows 有 elevated 与 unelevated 两种实现，unelevated 是较弱回退；配置或 readiness 不能替代实际执行证据。
- [Skills & Plugins](https://learn.chatgpt.com/docs/skills-and-plugins.md)：Skills 是可复用工作流；插件可组合 Skills 与 MCP/连接器。
- 锁定 Schema：`config/read`、`skills/list`、`mcpServerStatus/list`、`windowsSandbox/readiness` 和 `account/read`。

冻结的 ADR-0001 要求 SupportLevel 与 EnforcementLevel 分离：只有 Schema 或配置字段时 EnforcementLevel 必须为 `unknown`，unknown 能力不得进入产品承诺。本实现遵守该规则。

### MCP

- configured mode：default；
- readiness：ready；
- EnforcementLevel：unknown；
- security claim：not_inferred。

结果：通过。

## T4.3-C2 五种 SupportLevel 可区分

领域模型采用 ADR-0001 的枚举：

- supported；
- experimental；
- degraded；
- unsupported；
- unknown。

Renderer 为五种状态提供独立文字标签与样式，Electron Smoke 同时渲染五条合成 Native Capability 卡并读取 DOM 验证。真实 Probe 只输出有证据的状态：

- 合法响应：supported；
- 合法但存在 Skill 错误、Sandbox 未配置或需更新：degraded；
- 请求失败且错误原因没有精确分类：unknown；
- 不根据 Schema 存在自动输出 experimental 或 unsupported。

这样避免“为了覆盖状态而伪造当前 Runtime 事实”。

结果：通过。

## T4.3-C3 不覆盖或虚构 Codex 原生安全能力

Tsukiori 不修改 config、Skills、MCP 或 Sandbox 设置，只读取 app-server 的投影。Probe 不调用 `config/value/write`、`config/batchWrite`、`skills/config/write`、`config/mcpServer/reload` 或 `windowsSandbox/setupStart`。

SupportLevel 描述“Native API/清单能否读取”；EnforcementLevel 单独描述安全控制证据。即使 readiness 为 ready，Sandbox 卡仍显示 `runtime_native · enforcement=unknown`。Worktree、Permission Broker 或 Electron sandbox 均不会被冒充为 Codex 原生 Sandbox。

结果：通过。

## T4.3-C4 Runtime 专属能力不提升为公共能力

每个 Capability 都固定包含：

```json
{
  "scope": "runtime_native",
  "enforcementLevel": "unknown"
}
```

Snapshot 不含 `commonCapabilities`。Renderer 面板标题为 “CODEX NATIVE CAPABILITIES”，并显示“Runtime 专属能力；不自动提升为公共 Adapter 能力”。合同测试断言所有五项均为 native scope，Fixture 明确记录 `nativeCapabilitiesPromotedToCommon=false`。

结果：通过。

## 失败注入与修正记录

1. Fake Runtime 对 Skills 注入一个解析错误：Skills SupportLevel 降级为 degraded，错误正文和路径不进入 Snapshot。
2. Fake Runtime 返回 `windowsSandbox/readiness=updateRequired`：Sandbox readiness 降级，Enforcement 仍为 unknown。
3. Fake Runtime 对 `mcpServerStatus/list` 返回协议错误：由于 Adapter 当前不持久化精确错误码，MCP 保守标为 unknown 和 not_committed，而非猜测 unsupported。
4. 首次 Electron Smoke 使用全局 `[data-field="enforcement"]` 选择器，新增能力卡后误读 Sandbox unknown；修正为 `.permission-card` 限定选择器，使 Permission 与 Native Capability Enforcement 分开验证。
5. 实际本机 Probe 返回 readiness ready；报告没有把该结果升级成 os_sandbox/runtime_sandbox。
