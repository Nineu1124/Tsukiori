## 结论

T1.3 的五个 Checkpoint 均已实现并由真实文件数据库验证。新增纯领域包 `@tsukiori/domain` 和持久化包 `@tsukiori/database`，保持 UI/协议/Daemon 与数据库驱动解耦。数据库使用 SQLite WAL、foreign keys、busy timeout、Drizzle Schema 和 better-sqlite3；核心记录、Durable Operation、事件、权限和受限 Blob 引用均可关闭后重开恢复。

Lifecycle、Activity、Health 和 Workspace 使用四张独立投影表，各自带 `sourceEventId` 与 `updatedAt`。更新 Activity 不会覆盖 Lifecycle/Health；Worktree `active` 明确映射为 Workspace `clean`。Migration v1 建立核心事实表，v2 建立正交投影；测试覆盖空库直达 v2、v1 Fixture 升级到 v2，以及 v2 再次打开不重复执行。

所有 JSON 字段和 Blob 共用同一个写入前 `SecretGuard`。禁止的字段名、已知 Secret 值、Bearer/API Key/Private Key 等凭据形态与超限数据会在 SQLite、WAL 或 Blob I/O 前抛出 `PersistenceBoundaryError`。公开 Fixture 和测试数据不包含真实 Prompt、源码、SID、路径身份或凭据。

## 包与依赖边界

```text
@tsukiori/domain
        │
        ▼
@tsukiori/database ──► better-sqlite3 / Drizzle

@tsukiori/protocol ──► Desktop / Daemon / Testkit
```

- Domain 只含领域类型，不依赖应用、数据库或协议。
- Database 只依赖 Domain 和固定版本数据库库，不依赖 Desktop/Daemon。
- Daemon 仍只依赖 Protocol；数据库接入 Daemon bootstrap 将在需要恢复管理器时通过显式 composition root 完成。
- `tests/host/package-boundary.test.mjs` 解析实际 manifest 并固定上述方向。

## T1.3-C1 核心领域记录

已持久化并验证关闭/重开：

- `execution_environments`：环境类型、路径语义、Git/Shell 与 capability JSON。
- `projects`：环境绑定、根目录、Git 根、repository identity 与 setup/cleanup actions。
- `sessions`：Runtime identity、write mode 与初始三类状态。
- `session_turns`：Turn identity、状态、受保护 user input JSON 与时间。
- `worktrees`：环境/Session 绑定、分支、base ref/SHA 与生命周期。
- `process_records`：PID、parent PID、daemonBootId、start time、fingerprint 与 spawnNonce；不只依赖 PID。

外键模式在每次连接启用。路径均作为本地文本保存；本任务不上传或同步数据库。

结果：通过。

## T1.3-C2 Operation、Event、Permission 与 Blob

- `operations` 以唯一 `operation_id` 保存 prepared/running/committed/failed/uncertain 事实和受保护 JSON。
- `session_events` 实现 `(stream_id, stream_sequence)` 去重，并为 `(runtime_handle_id, connection_epoch, runtime_event_id)` 建唯一索引。
- `permission_requests` 实现 Runtime Handle + Epoch + Request ID 唯一约束，支持 pending/resolved/invalidated/expired。
- `blob_objects` 只保存内容哈希、相对路径、大小、媒体类型和创建时间；事件只保存 Blob ID 引用。
- Blob 使用 SHA-256 两级相对路径、根目录逃逸检查、排他临时写入和 rename；重复内容幂等，不残留 `.tmp`。

结果：通过。

## T1.3-C4 Migration

Migration runner 的行为：

1. 先幂等创建 `schema_migrations`。
2. 按严格递增版本执行尚未应用且不高于 target 的迁移。
3. 每个版本的 DDL、迁移记录与 `user_version` 在同一事务提交。
4. 无效 target（负数、非整数、超过最新版本）直接拒绝。
5. `readMigrationVersions` 作为可观察证据返回已应用版本。

验证矩阵：

| v1 Fixture | v2 | `[1, 2]`，投影表可用 |
| v2 | v2 再打开 | 不重复执行，版本保持 `[1, 2]` |

结果：通过。

## T1.3-C5 Secret 不进入 SQLite/WAL/Blob

同一 `SecretGuard` 位于 Repository JSON 序列化和 Blob 文件写入之前：

- 递归拒绝 `api_key/secret/token/password/cookie/authorization/private_key` 等字段名。
- 拒绝调用方登记的已知 Secret 值。
- 拒绝 Private Key header、Bearer、`sk-` 和 AWS access key 等凭据形态。
- JSON 上限 256 KiB，Blob 上限 10 MiB。
- 循环对象和非 JSON 类型在写入前拒绝。

失败注入分别尝试 Operation JSON 已知 Secret、`api_key` 字段、Event Bearer 和 Blob 已知 Secret；四次都抛边界错误，三张事实表计数保持 0。随后写入安全事件并扫描测试目录的数据库、WAL、SHM 和 Blob 文件，Secret marker 不存在。

结果：通过。

本机直接 prebuild-install 两次分别遇到 `ECONNRESET` 和 timeout，随后通过 GitHub CLI 从 `WiseLibs/better-sqlite3` 官方 v12.8.0 Release 下载同一资产：

## 失败与修正记录

1. better-sqlite3 13.0.2 回退 node-gyp 后因无 VS Build Tools 失败。改用明确提供 Node 24 官方预编译资产的 12.8.0。
2. 12.8.0 的 GitHub Release 直连发生 reset/timeout。通过已认证 GitHub CLI 获取官方资产并记录 archive/binary 哈希。
3. 首次 strict typecheck 发现 optional `knownSecrets` 在 exact optional 模式下不能显式传 undefined；改为只在存在时传属性。
4. Worktree `active` 与 Workspace State 没有同名值；按架构语义显式映射为 `clean`，避免强制类型转换隐藏差异。
5. 重复内容 Blob 在 Windows rename 冲突时可能残留临时文件；改为目标存在则复用，竞争失败且目标已出现时删除临时文件，并加入断言。
