# T3.3 OpenCode 权限、控制与恢复报告

- 任务：T3.3
- 完成日期：2026-08-02
- 平台：Windows x64 / Windows Native Git Worktree
- Runtime：OpenCode 1.18.4
- SDK：`@opencode-ai/sdk` 1.18.4（v2）
- 权限边界：OpenCode Runtime 暂停请求，Host 通过 `permission.reply` 决策

## 结论

T3.3 的五个 Checkpoint 均已通过。OpenCode 权限事件进入公共 Permission Broker，Permission Card 明确显示实际 `interceptable` Enforcement Level；Host 只提供 Runtime 真正支持的 allow once 与 deny once。Cancel 使用 Runtime Session ID 调用 `session.abort`，Resume 使用 `session.get` 验证原 Session，不依赖保存或重放原始 Prompt。重连前会使旧 Connection Epoch 的待决权限失效。两个独立 Worktree Scope Server 的崩溃注入证明一个 Runtime Handle 退出不会影响另一个；失败 Session 最终为 `stopped/interrupted_runtime`，不会伪装为 running。

T0.1 已对 OpenCode 1.18.4 真实 Permission、Abort 与同 Session Resume 完成协议验证；T3.3 在正式 Adapter 上用公开无凭据 Runtime Fixture 验证 Host 映射、持久化、旧 Epoch 防护与双进程隔离。

## Checkpoint 证据

### T3.3-C1 权限请求显示实际 Enforcement Level

- `permission.asked` / `permission.v2.asked` 只在成功归一化和完成 Host Session 路由后提交 Permission Broker。
- OpenCode 已暂停并等待 Host 回复，因此 Enforcement Level 为 `interceptable`，不会错误标记为 OS sandbox 或 Runtime sandbox。
- `bash`、`edit`、`read`、`external_directory`、`network` 映射到公共 Permission Category/Risk；未知类别保持 `other/high`。
- Permission Card 保存 category、risk、scope、available decisions、Runtime Handle 和 Connection Epoch。
- Runtime 只支持 `once`、`always`、`reject`；为避免把 Runtime 的 broad always 错表述为 Host session/project scope，T3.3 仅开放 `allow_once` 与 `deny_once`。
- Renderer 已通过固定 Preload Snapshot 展示 `enforcementLevel`，不由不可信事件生成 HTML。
- 结果：通过。

### T3.3-C2 Cancel 与 Resume 不重放原始 Prompt

- Cancel 从 Host Session 读取 Runtime Session ID，并调用 `session.abort`；不存在 Prompt 重建路径。
- Abort 前 Session Activity 变为 `interrupting`；成功后 Turn 为 `interrupted`、Session 为 `idle/healthy`。
- Abort HTTP 响应前到达的 `session.idle` / `session.error` 通过 cancelling 状态映射为 interrupted，不误记 completed/failed。
- Resume 使用 `session.get` 校验原 Runtime Session ID；随后新 Turn 仅使用新的调用方输入。
- SQLite 中每个 Host Turn 的 `userInput` 只保存 `{ source: "opencode", persistedText: false }`；Cancel 前输入和 Resume 后输入均未持久化。
- 结果：通过。

### T3.3-C3 旧 Epoch 权限无法在恢复后响应

- 每项 pending permission 同时绑定 Runtime Handle、Runtime Request ID 和当前 Connection Epoch。
- `recoverEventStream` 在切换 Epoch 前调用 Permission Broker `invalidateEpoch`，生成审计记录并关闭等待权限 Attention。
- 被失效请求转为 `invalidated`，并产生 `recovery_uncertain` Attention；Bridge 清空 Runtime reply 映射。
- 使用旧 Permission ID/Epoch 的后续决策在发出任何 Runtime 网络请求前被拒绝。
- 测试观察到 `invalidatedPermissionCount=1`、新旧 Epoch 不同、Permission Audit 为 invalidated。
- 结果：通过。

### T3.3-C4 一个 OpenCode Server 崩溃不影响其他 Handle

- 同一 Adapter/Profile 在同一 Worktree 启动两个独立 loopback Server，PID 不同、密码和 SSE 读取器独立。
- 标记 Session 所在 Server 以退出码 23 强杀；另一个 Handle 的数据库状态仍为 ready，global SSE 仍 connected。
- 健康 Handle 在第一个 Server 退出后继续完成新的 Session Turn。
- Process Record 显示崩溃进程 exited、健康进程 running。
- 结果：通过。

### T3.3-C5 不可恢复状态不伪装运行中

- Runtime 意外退出先持久化 Handle/Process 的 exited 状态，再投影绑定 Session。
- 所有绑定 Session 变为 `activity=stopped`、`health=interrupted_runtime`；活动 Turn 为 interrupted，已经失败的 Turn 保留 failed 终态。
- Turn 启动请求因进程退出失败时，会读取已持久化 Runtime Handle 状态并选择 stopped/interrupted_runtime，而不是回写 running。
- Runtime 退出同步 Abort global SSE，并显式结束 stream iterator，防止资源泄漏和 Host 测试进程挂起。
- 测试断言失败 Session 不是 running，并验证健康 Handle 不受影响。
- 结果：通过。

## 失败与修正记录

1. 首轮双 Handle 崩溃测试的业务断言在约 1.7 秒通过，但 Node runner 不退出。进程检查确认 Fake Server 已结束，残留为测试 worker；根因是异常退出 Handle 的 `stop()` 早退，Bridge SSE AbortController 未被显式终止。`runtimeExited()` 现同步 abort 并关闭 iterator，完整五场景在约 12 秒内收敛。
2. Permission SSE 可早于 `promptAsync` HTTP 204 到达。Start Turn 现保护 waiting_permission / waiting_user_input 与所有终态，较晚的 running 不会覆盖它们。
3. Cancel 的 `session.idle` 可早于 abort HTTP 响应。新增 cancelling 状态以稳定映射 interrupted。
4. Runtime 的 `always` 含义不能安全等同于 Host 的 session/project scope；该能力未提升，UI 不提供相应决定。

## 安全边界

- Permission metadata、原始 patterns、工具输入输出和 Prompt 不写入公开 Fixture；Card 只保留 permission 类型与 pattern 数量。
- Runtime Request ID 通过有界 Host Permission ID 映射；API Key、Server 密码和 Authorization 不进入参数日志或数据库。
- 旧 Epoch 在任何 Runtime reply 前校验，防止重连后误响应过期权限。
- Worktree 与独立 Server 提供变更和故障隔离，不被描述为安全沙箱。
