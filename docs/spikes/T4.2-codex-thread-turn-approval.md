## 结论

T4.2 的五个 Checkpoint 均已实现。Codex app-server 的 Thread、Turn、Item 和 notification 通过每个 Runtime Handle 唯一的 JSONL stdout 读取器进入 Host；HostSession/HostTurn ID 与 Runtime Thread/Turn ID 分开保存；事件按 Thread 路由并对完全相同的无 ID 重放去重。

Command、File 和结构化 Permissions Approval 均通过 Permission Broker 形成可审计的 Permission Card。只有 app-server 主动发出可响应的服务端请求时才标记为 `interceptable`。T0.2 已真实观察到 Command 与 File Approval；结构化 Network Approval 仅完成合成合同测试，当前真实 Runtime 支持级别继续保持 `unknown`。

## T4.2-C1 Thread、Turn、Item 映射

`CodexSessionBridge` 将 Runtime Thread ID 绑定到既有 HostSession，将 Runtime Turn ID 映射到稳定派生的 HostTurn ID。EventNormalizer 新增显式 `hostSessionId` 与 `hostTurnId`，因此：

- `event.sessionId` / `event.turnId` 保存 Host ID；
- `event.runtimeSessionId` / `event.runtimeTurnId` 保留 Codex 原生 ID；
- Session 表保存 Runtime Thread ID；
- Turn 表保存 Runtime Turn ID；
- HostSession 的 activity/health 与 HostTurn status 随生命周期事件更新。

覆盖 `thread/started`、`thread/status/changed`、`turn/started`、`turn/completed`、`item/started`、`item/completed` 与 `item/agentMessage/delta`。消息 Item 映射为 assistant event，其他 Item 保守映射为 tool event 或 native event。

结果：通过。

## T4.2-C2 Command、File、Network Approval

Adapter 只接受三种已知 Approval 服务端请求：

| app-server 请求 | Permission Category | Enforcement Level | 证据 |
| --- | --- | --- | --- |
| `item/commandExecution/requestApproval` | `shell` | `interceptable` | T0.2 真实事件 + T4.2 合同 |
| `item/fileChange/requestApproval` | `file_write` | `interceptable` | T0.2 真实事件 + T4.2 合同 |
| `item/permissions/requestApproval` 且含 network | `network` | `interceptable` | T4.2 合成合同；真实支持 unknown |

Command/File 的一次允许、拒绝和取消分别安全映射为 `accept`、`decline`、`cancel`。结构化 Permissions 允许时仅回送 Runtime 原请求中的 permissions 和 turn scope；拒绝时清空 fileSystem/network。其他服务端请求不会被误当 Approval，会返回脱敏的 `rejected` JSON-RPC 错误。

Permission Card 不持久化原始命令、文件内容或网络载荷，只保存类别、风险、执行级别和通用作用域。

结果：通过。

## T4.2-C3 Interrupt、Resume 与旧 Epoch

`interrupt()` 从 HostTurn 查出 Runtime Turn ID，并与 Session 中的 Runtime Thread ID 一起调用 `turn/interrupt`。`resume()` 调用 `thread/resume` 后重新绑定同一 Thread；`startThread()` 和 `startTurn()` 同样记录双向映射。

Runtime Handle 退出时，Adapter 使该 connection epoch 的待处理审批失效：

- PermissionRequest 状态变为 invalidated；
- waiting_permission Attention 被解析；
- 生成 recovery_uncertain Attention；
- 生成 invalidated Audit；
- 待响应 Promise 被拒绝；
- 旧 Epoch 或已失效请求不能再响应。

正常 stop 与异常 exit 都执行失效流程，但没有待处理请求时不生成多余恢复项。

结果：通过。

## T4.2-C4 未知 Item/Event

未知方法和未来 Item 类型进入 `native.event`，先递归脱敏敏感键和值，再执行字节限额。超限载荷只保留安全 preview、content hash、`truncated=true` 和 `redacted` 标记。

测试注入超过 2 KB 的未知事件和敏感字段，验证公开事件与 SQLite 均不含原值；紧随其后的已知流式文本仍被接受，未知事件不会阻断会话。

结果：通过。

## T4.2-C5 多 Thread 隔离与去重

合同测试并行绑定三个 Runtime Thread 到三个 HostSession，并各自创建独立 HostTurn。SQLite 分组验证事件只进入对应 Session，Runtime ID 不会替代 Host ID。

每个 Handle 只在 Adapter 的 `#attach()` 中创建一个 stdout readline。该读取器按消息形状分发：

1. 无 method 且有 id：客户端请求响应；
2. 有 method 且有 id：app-server 服务端请求；
3. 有 method 且无 id：notification。

显式 Runtime Event ID 优先用于去重。无 ID 的非 delta 事件对完整结构化载荷取 SHA-256，因此完全相同的重放只应用一次，而同一 Thread 的不同 status 更新不会被误删。Delta 没有稳定 ID 时使用单调本地序号，避免错误吞掉合法重复文本。

结果：通过。

## 失败注入与修正记录

1. 审查首版去重键时发现其只包含 method、Thread、Turn 和 Item，会把同一 Thread 的不同状态更新误判为重复。修正为包含完整 JSON 载荷的 Hash，并增加 idle → active → active 重放测试。
2. 注入未知 Item/Event 的 2 KB 载荷和敏感字段；载荷被截断、字段被脱敏，后续 delta 正常进入。
3. 注入错误 connection epoch 响应；Broker 拒绝，随后 Epoch 失效产生恢复不确定项。
4. 注入不支持的服务端请求；Bridge 不创建 Permission Card，Adapter 只返回固定 `rejected`，不回显异常或原始载荷。
5. Fake app-server 同一 stdout 交错发送客户端响应、notification 和 Approval 请求；单读取器完成分发，审批响应正确回到原 request id。
