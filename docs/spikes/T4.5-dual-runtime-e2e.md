# T4.5 OpenCode/Codex 双 Runtime 闭环实施报告

## 结论

T4.5 的五个 Checkpoint 均已通过。无凭据 Windows E2E 在同一 Project 下创建 1 个 OpenCode Session 和 2 个 Codex Session，每个 Session 拥有独立 Worktree、Runtime Handle、Connection Epoch 和事件映射；三个 Session 连续运行 5 轮。OpenCode 与 Codex 的两份修改分别 Review/Commit 后，通过两个 Integration Worktree 串联验证。第 6 轮强杀 OpenCode Server，Codex 仍能完成新 Turn 且 Handle/Session 保持健康。

## 环境与 Fixture

- Windows Native
- OpenCode Fixture `1.18.4`
- Codex app-server Fixture `0.146.0`
- 三个 Host Session / 三个 Runtime Handle / 三个独立 Worktree
- 连续轮数：5
- 脱敏结果：`tests/fixtures/dual-runtime/t4.5-result.json`
- 自动化：`tests/dual-runtime/dual-runtime-e2e.test.mjs`

公开 CI 使用 Fake Runtime，不要求 DeepSeek/OpenAI 凭据。真实 OpenCode/DeepSeek 与真实 Codex 生命周期分别已由 T3/G3、T4.1–T4.3 验证。

## 实现补充

- Fake Codex app-server 新增 Thread/Turn 生命周期、Item Notification 和固定 Worktree 修改，用于公开 CI 的确定性协议验证。
- Fake OpenCode 新增 `crashOnPromptCount`，可在连续运行的指定轮次强杀 Server。
- Codex Session Bridge 把 Turn `completed/failed` 投影到公共 Permission Broker 的 Attention Center；Source Ref 包含 Host Session ID，避免不同 Handle 使用相同 Runtime Turn ID 时冲突。
- GitDiffService 与 IntegrationMergeService 直接复用 T4.4 的审计、Commit 和临时 Integration Worktree 安全边界。

## T4.5-C1 同一 Project 同时运行 OpenCode 与 Codex

E2E 只注册一个 Project，随后创建：

- `dual-opencode`：OpenCode Profile/Handle/Session；
- `dual-codex-a`：Codex Profile/Handle/Thread；
- `dual-codex-b`：第二个 Codex Handle/Thread，用于三 Session 持续与崩溃隔离。

三个 Handle 并行启动，三个 Session 每轮并行 Start Turn，连续 5 轮均回到 `idle`。

结果：通过。

## T4.5-C2 不同 Worktree、统一 Attention Center

三个 Workspace Binding 的 Worktree ID 和 canonical path 均唯一。Fake Runtime 只写绑定 Worktree：

- OpenCode：`alpha-runtime.txt`；
- 两个 Codex：各自 Worktree 的 `codex-runtime.txt`。

测试逐路径断言不存在跨 Runtime 文件，主工作区也不存在任何 Runtime 文件。OpenCode/Codex Turn 完成事项均通过同一 Permission Broker 进入 Attention；每个 Host Session 至少有一条独立 `completed` Attention。

结果：通过。

## T4.5-C3 分别 Review、Commit 和 Integration Worktree 合并

- OpenCode Session：Stage、Commit、审计 Session Commit Diff；
- Codex A Session：Stage、Commit、审计 Session Commit Diff；
- Commit Hash 不同且分别绑定各自 Worktree；
- 第一次 Integration 以 `main` 为 Target 合并 OpenCode Commit；
- 第二次 Integration 以第一次的 Integration Branch 为 Target 合并 Codex Commit；
- 最终 Result Commit 同时包含两个 Runtime 文件；
- 两个 Integration Worktree 均验证后清理，主工作区 HEAD/Status 不变。

结果：通过。

## T4.5-C4 任一 Runtime 崩溃不影响另一 Runtime

Fake OpenCode 配置在第 6 个 Prompt 强制 `exit(23)`。Host 观察到：

- OpenCode Turn 启动失败；
- OpenCode Session 进入 `stopped/interrupted_runtime`；
- 旧 Epoch 权限/输入请求按 Adapter 规则失效；
- Codex B 随后创建新 Turn 并完成；
- Codex Handle 仍为 `ready`，Session 为 `idle/healthy`。

两个 Codex 进程和独立 Daemon 控制状态未受 OpenCode 子进程退出影响。

结果：通过。

## T4.5-C5 三个并行 Session 持续无串线和代码污染

连续 5 轮后，SQLite `session_events` 对三个 Session 分组均至少 5 条事件，且 Event Normalizer/Bridge 只按 Runtime Thread/Session Mapping 写入对应 Host Session。代码污染检查覆盖六个正反路径和主工作区。持久化数据扫描确认不含各轮 Prompt、崩溃指令或用户源码。

结果：通过。

## 安全与数据边界

- Prompt 只传给 Runtime，Host Turn 仍为 `persistedText:false`。
- Fake Runtime 修改为固定脱敏内容；Fixture 不保存文件内容或 Diff。
- 每 Runtime Handle 使用独立进程、cwd、Connection Epoch 和事件读取器。
- Attention Source Ref 包含 Host Session，避免跨 Handle ID 碰撞。
- 两份合并只在 Integration Worktree 验证，不自动更新 main。
- 公开 CI 不配置 Provider Key。
