## 总结

新增 `@tsukiori/credential-broker`，使用 Windows Credential Manager Generic Credential API（`CredWriteW`、`CredReadW`、`CredDeleteW`）保存 Provider/API Secret。应用持久层只看到不可推导 Secret 的 `secretref:<uuid>`；实际 Secret 通过 helper stdin 写入 Credential Manager，不进入命令行参数、环境审计、SQLite/WAL/Blob、Renderer 或公开 Fixture。

Daemon 的持久租约已从明文 `bootstrapToken` 改为 `bootstrapSecretRef`。新 GUI 只有在相同 Windows 用户下从 Credential Manager 解析引用、完成 CurrentUserOnly Named Pipe challenge-response，并校验 Instance ID/PID/协议后才能附着。Daemon 正常停止或发现死亡租约时删除对应 OS Credential；`keep` 策略保留引用供下一 GUI 重连。

## T5.2-C1 OS 凭据库与指定 Runtime 注入

Credential Broker 的绑定包含 Runtime Type、Runtime Profile ID 和允许的环境变量名。读取时三者必须与存储时完全一致；错误 Profile 会在注入前拒绝。启动 Runtime 时：

1. 从当前用户 Windows Credential Manager 读取 Secret；
2. 从子进程环境删除所有已知 Provider Secret 变量；
3. 只加入当前绑定的一个 Secret；
4. 使用结构化 `spawnSync`、`shell:false` 启动指定 Runtime；
5. 审计只记录 executable、非敏感 args 和环境变量名称，不记录值。

真实测试将 DeepSeek Fixture Secret 注入绑定进程，同时向父环境放入另一个 OpenAI Fixture Secret；子进程只收到 DeepSeek 绑定，OpenAI 变量不存在。错误 Runtime Profile 读取被拒绝。

结果：通过。

## T5.2-C2 Secret 不进入不可信或持久化表面

- Renderer/Preload 不导出 API Key、Secret Reference 或 Credential Broker 通道；
- Secret 不作为命令行参数或外部可见审计值；
- Daemon Lease 只包含 `bootstrapSecretRef`，不包含 `bootstrapToken`；
- Database `SecretGuard` 在 SQLite/WAL/Blob 写入前拒绝已知 Secret、敏感键和凭据形态；
- Runtime Event 先递归脱敏再限长；
- Credential child stdout/stderr 只返回匹配布尔值，不回显 Secret；
- Fixture、报告、日志摘要和公开 CI 无真实凭据。

临时数据库、WAL、SHM 和 Blob 目录经过字节扫描，Fixture Secret 不存在。

结果：通过。

## T5.2-C3 持久权限规则收敛

`allow_session` 与 `allow_project` 现在都必须使用结构化 Matcher。包含 `raw` 或 `command` 原始 Shell 字符串的请求不能产生持久 Allow；`allow_project` 继续拒绝 `observable_only` 与 `opaque` Enforcement Level。一次性 Allow 和 Deny 审计行为保持不变。

结果：通过。

## 失败与修正

1. Credential helper 首次编译时 `FILETIME` 同时命中两个 .NET 命名空间；改为完整限定 `System.Runtime.InteropServices.ComTypes.FILETIME`，真实写入/读取/删除随后通过。
2. Desktop 引入 Credential Broker 后，Package Boundary Test 正确报告依赖集合变化；测试更新为显式允许 Credential Broker，并同时把此前新增的 Recovery Manager 纳入包图审计。
3. 初版 Runtime 环境注入会继承父进程中其他 Provider Secret；改为先删除全部允许列表中的 Secret 变量，再只注入当前绑定变量，并增加跨 Provider 隔离测试。

这些修正均提高安全约束，没有降低测试标准。
