## 结论

T0.2 的五个 Checkpoint 均已完成。两个独立 app-server 进程可以重复执行 initialize/initialized 与 account/read；Thread、Turn、Item 能以原生 ID 关联；两个 Runtime Handle 各自只有一个 stdout 事件读取器且没有跨 Handle 串线；命令与文件审批可被宿主拦截并拒绝；网络场景可在命令层被拦截，但本次没有观察到结构化网络审批上下文，因此网络专属审批能力保持 `unknown`；Turn 可中断，持久 Thread 可由新 app-server 进程恢复并继续完成新 Turn。

## Checkpoint 证据

### T0.2-C1 initialize/initialized 与认证状态

- 两个独立进程分别发送一次 initialize，收到包含 userAgent 的响应后发送 initialized。
- 两个 Handle 分别执行 account/read，均只记录 `authenticated: true`。
- 没有读取、打印或保存认证令牌、cookies 或认证存储。
- 结果：通过。

### T0.2-C2 Thread、Turn、Item 生命周期映射

- 两个 Handle 分别创建持久 Thread，并发启动最小 Turn。
- 两个 Turn 均为 `completed`。
- 观察到 `thread/started`、`turn/started`、`item/started`、`item/completed`、`turn/completed`。
- 脱敏 Fixture 保留 Thread/Turn/Item 关联字段，真实 ID 被稳定占位符替换。
- 结果：通过。

### T0.2-C3 Runtime Handle 独立事件读取器

- Harness 同时启动两个 app-server 子进程。
- 每个进程只由其 JsonlClient 实例读取 stdout；请求响应、服务端请求、通知分别分发。
- Handle A 未观察到 Handle B 的 Thread ID，Handle B 也未观察到 Handle A 的 Thread ID。
- 结果：通过。

### T0.2-C4 Command、File、Network Approval 范围

| 场景 | 实际事件 | 宿主动作 | 结论 |
| --- | --- | --- | --- |
| 命令写入场景 | `item/commandExecution/requestApproval` | 返回 decline | command approval 为 interceptable |
| 原生文件补丁场景 | `item/fileChange/requestApproval` | 返回 decline | file approval 为 interceptable |
| 指定域名 HEAD 场景 | `item/commandExecution/requestApproval` | 返回 decline | 场景在命令层可拦截；未见结构化网络上下文 |

生成的非实验 Schema 声明 `item/permissions/requestApproval` 和网络权限字段，但真实网络场景没有产生该事件，也没有在 command approval 中附带 `networkApprovalContext` 或网络策略修订。因此 V1 不能把 Codex 网络专属审批标为 supported；当前支持级别和执行级别均为 `unknown`。这一负面结果是本 Checkpoint 要求的“实际范围”结论，不以 Schema 存在代替运行时证据。

### T0.2-C5 Interrupt、Resume 与 Schema Hash

- 启动一个长命令 Turn 后立即调用 `turn/interrupt`，最终状态为 `interrupted`。
- 关闭原 Handle，启动新 app-server 进程并调用 `thread/resume`。
- 恢复响应中的 Thread ID 与原 Thread 一致，恢复后的新 Turn 为 `completed`。
- 非实验完整 Schema bundle 的 SHA-256 为 `776ab888b2e673311a4c53ed086d66b061dcfdc8ca595b4cf43220c2b3d04368`。
- 结果：通过。

## 失败注入与恢复记录

1. 使用 0.142.5 运行真实 Turn：协议启动正常，但模型服务拒绝旧客户端。结论：Runtime 版本与 Schema 必须共同锁定；不能只做握手。
2. 使用 0.146.0 重试：模型服务兼容，Turn 完成。
3. 本机 WebSocket sampling 多次超时：Codex 自动回退 HTTPS 后成功。结论：传输降级应作为诊断事件，不应被误判为 Thread 失败。
4. 审批统一返回拒绝：没有越权写入、文件补丁或实际网络访问。
5. 进程边界恢复：旧 Handle 关闭后，新进程成功恢复同一 Thread。

## 安全与脱敏

- Harness 仅在随机临时 Git 仓库运行，结束后删除该目录。
- 公开 Fixture 不含完整 Prompt、模型输出、原始命令、真实路径、主机名、账号、令牌或认证存储。
- ID 被稳定映射为占位符；命令、路径、文本、原因、URL、host、策略修订均脱敏。
- 真实 Provider 测试只在本机运行；CI 仅重放公开 Fixture 和校验 Schema Hash。
- 网络专属能力保持 `unknown`，没有从字段存在推导为 supported。

## 已知问题

- 当前系统全局 npm Codex 仍为 0.142.5；Spike 使用私有 0.146.0。正式 Adapter 必须实现版本探测和最低兼容版本策略。
- WebSocket 在本机不可用并回退 HTTPS，延迟约增加两分钟。
- 结构化网络审批未验证，T4.2 前必须保持 unknown，不得提供网络粒度持久 Allow。
