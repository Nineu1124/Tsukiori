- 锁定版本：0.146.0

## 结论

T4.1 的四个 Checkpoint 均已实现。新增 `@tsukiori/adapter-codex`，完成 Windows Native Codex CLI 发现、版本 Probe、版本化 Schema 锁定、stdio JSONL app-server 启停、`initialize/initialized`、`account/read` 认证状态投影、ProcessRecord、Runtime Handle 和生命周期审计。

正式 Adapter 不读取 `auth.json`、keyring 或环境中的凭据内容，也不发起登录。认证投影只保存 `authenticated`、`authSource` 和 `requiresOpenaiAuth`。账号、邮箱、计划、token、Codex Home、stderr 内容和原始协议事件均不持久化。

## 官方协议基线

本任务按 2026-08-02 刷新的 OpenAI Codex 官方手册实现：

- [Codex App Server](https://learn.chatgpt.com/docs/app-server.md)：app-server 适用于富客户端深度集成；stdio 使用 JSONL；连接必须先 `initialize`，再发送 `initialized`；Schema 由当前 Codex CLI 版本生成。
- [Authentication](https://learn.chatgpt.com/docs/auth.md)：Codex 本地认证可来自 ChatGPT 或 API key，凭据可存于本地文件或 OS credential store，宿主不应读取明文存储。
- [Codex app-server source](https://github.com/openai/codex/tree/main/codex-rs/app-server)：协议实现的开源来源。

## T4.1-C1 路径、版本、认证来源与兼容性

发现顺序支持显式候选、全局 npm `codex.js` 和 PATH 中的原生 `codex.exe`。候选必须是存在的文件，并通过结构化 `--version` 探测。Profile 保存 canonical executable、启动前缀、发现来源、版本、Execution Environment、Schema Hash 和兼容性。

认证只调用：

```json
{ "method": "account/read", "params": { "refreshToken": false } }
```

已知 account type 映射为 `chatgpt`、`apikey`、`chatgpt_external_tokens`、`amazon_bedrock` 或 `access_token`；未来未知类型保留 `unknown`。无 account 返回 `none`。

真实本机私有 0.146.0 Probe 结果：

- 版本：0.146.0；
- 兼容性：supported；
- initialize/Schema：通过；
- 当前认证：`authenticated=false`、`authSource=none`、`requiresOpenaiAuth=false`；
- 正常停止后 Handle：stopped；
- 输出不含凭据。

该结果与 T0.2 当时观察到的 ChatGPT 登录状态不同，因此当前报告采用最新真实 Probe，不沿用旧认证结论。

结果：通过。

## T4.1-C2 按版本 Schema 校验 initialize/initialized

Adapter 加载 0.146.0 非实验 manifest，重新计算完整 bundle 的 SHA-256 和字节数，必须与 manifest 同时匹配。InitializeResponse 根据锁定 bundle 的 required、直接 type 和 `allOf/$ref` type 验证，包括：

- codexHome；
- platformFamily；
- platformOs；
- userAgent。

验证通过后才发送 `initialized` 并进入 ready。失败 Fixture 故意省略 required 字段，Handle 进入 failed、ProcessRecord 终结、失败 audit 落盘后才返回错误。

结果：通过。

## T4.1-C3 Handle 启停、异常退出和 Re-Probe 审计

SQLite v6 保存：

- RuntimeProfile：发现、版本、Schema、认证和兼容性；
- RuntimeHandle：connection epoch、PID、状态、平台、退出码和 expected exit；
- RuntimeAudit：discover/probe/schema_lock/start/initialize/auth_probe/stop/exit/reprobe；
- ProcessRecord：PID、daemon boot ID、start time、nonce、executable fingerprint 与状态。

测试覆盖正常 stop 和退出码 23 的异常退出。Schema 启动失败最初暴露退出审计晚于数据库关闭的竞态，现失败 `start()` 会等待子进程 exit 和持久化完成再返回。Re-Probe 保留 Profile ID 和 createdAt，刷新版本与兼容性。

结果：通过。

## T4.1-C4 高于 maxTestedVersion 的降级

版本策略为：

- 低于 minimum：`incompatible_older`；
- 高于 maximum tested：`unverified_newer`；
- bundle Hash/bytes 或同范围版本不匹配：`schema_mismatch`；
- 精确锁定且 Hash 一致：`supported`。

0.147.0 Fixture 会进入 `unverified_newer`。默认 `start()` 明确拒绝，且不会创建 RuntimeHandle 或进程；UI 展示真实兼容性，不把新版本自动提升为 supported。0.145.0 同样以 `incompatible_older` 拒绝。

结果：通过。

## 认证状态 UI

Renderer 新增 Runtime 卡片，仅显示：runtime type、版本、Handle 状态、认证来源和兼容性。所有内容使用 `textContent`，不新增动态 HTML、Node integration 或任意 IPC。Electron smoke 验证卡片可见后再强杀 Renderer，Daemon 与 Fake Runtime 仍存活。

## 失败与修正记录

1. 首次 TypeScript 构建发现局部变量 `process: ProcessRecord` 遮蔽 Node 全局 `process`，导致环境变量读取类型错误；改名为 `processRecord`。
2. 首轮 Adapter 测试的七个功能断言通过，但 Schema 失败路径的子进程 exit audit 晚于测试关闭 SQLite，引发异步 activity；失败 start 现等待精确子进程退出后再返回。
3. 首次真实 Probe 使用临时数据库目录作为 app-server cwd，Windows 在进程退出后短暂锁住目录导致清理失败；改为仓库 cwd、临时目录只保存数据库，并清理两次已确认的遗留 Fixture 目录。
4. T0.2 曾观察到 ChatGPT 登录；本次真实 `account/read` 返回无账户且不要求 OpenAI auth。状态是外部可变事实，报告和 UI 使用本次 Probe 的 `none`，未读取认证存储验证原因。
