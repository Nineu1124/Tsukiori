# T3.4 OpenCode Windows Alpha 用户闭环实施报告

## 结论

T3.4 的五个 Checkpoint 均已实现并通过可重复验证。新增 `@tsukiori/alpha-workflow` Host 组合层，把 Project 注册、独立 Worktree、OpenCode 1.18.4、DeepSeek Provider 选择、Session/Turn、Attention、Diff、Stage、Commit、Archive 与安全清理串成一个受 Session/Workspace Binding 约束的工作流。桌面端提供对应 Windows Alpha 操作面，Renderer 只能调用固定 Preload API，不能直接访问 Git、文件系统或 Runtime。

公开 CI 使用无凭据 Fake OpenCode，真实 Provider 能力继续引用 T3.1 已完成的本机证据：`dpsk/deepseek-v4-flash` 请求成功，数据出口为 `api.deepseek.com`。T3.4 E2E 不把 API Key、Prompt、模型输出或用户源码写入 Fixture。

## Checkpoint 证据

### T3.4-C1 项目 → Worktree → OpenCode + DeepSeek → 修改

E2E 每轮创建全新的临时 Git Repository 和本地 SQLite，注册 Windows Native Execution Environment，创建独立 Worktree，启动独立 Fake OpenCode Server，选择 `dpsk/deepseek-v4-flash`，创建 Session/Turn，并由 Fake Runtime 在绑定 Worktree 写入固定的 `alpha-runtime.txt`。测试同时断言主工作区不存在该文件。

真实 Runtime/Provider 的协议、认证、请求和 `api.deepseek.com` 数据出口已由 T3.1 本机 Probe 验证；公开 CI 仅替换模型输出与文件修改为确定性 Fixture。

结果：通过，两次完全独立的干净环境运行均成功。

### T3.4-C2 Attention Center 处理权限、输入、完成和失败

- 权限：`waiting_permission` 显示实际 `interceptable` Enforcement Level，并通过 `allow_once` 完成 Runtime Reply。
- 输入：`question.asked` 生成 `waiting_input`；回答经结构化二维字符串数组调用 Runtime API，数据库和事件 Fixture 均不含回答文本。
- 完成：`session.idle` 生成 `completed` 并关联 Host Turn。
- 失败：`session.error` 生成 `failed`，Session 进入 `idle/error`，不会伪装为运行中。
- Runtime 退出/重连：旧输入 Attention 被关闭；不确定状态进入 `recovery_uncertain`。

结果：通过。

### T3.4-C3 Review Diff、Commit、归档与安全清理

- `GitDiffService` 继续提供 Working、Staged、Session Commit 三类 Diff。
- Stage 只接受当前 Session 变更集中的相对路径，路径参数位于 `--` 之后。
- Commit 使用结构化参数、禁用 Hook/GPG、拒绝空 Staged Diff、冲突和多行 Subject。
- Commit Hash 与 Worktree ID、Session ID、Branch、Staged Paths 一并返回，并写入 Workspace Binding。
- Clean Worktree 归档后可删除；Dirty Worktree 请求清理时返回 `blocked`，Runtime 修改和 Worktree 均保留，主工作区不受影响。

结果：通过。

### T3.4-C4 Alpha 不展示未实现入口

Alpha UI 的可见入口固定为 Project、Worktree、OpenCode、DeepSeek、Attention、Diff、Commit 和 Archive。自动化测试确认不存在 Merge、Claude、ACP、WSL、macOS 或 Linux 的可操作控件/平台属性。能力数据中对应入口保持隐藏或不可操作，不提升为已支持能力。

结果：通过。

### T3.4-C5 Windows Alpha E2E 可重复

同一测试连续建立两个不同临时根目录、数据库、Repository、Worktree Root、Project、Session、Runtime Profile、Runtime Handle 和 OpenCode Server；每轮均完成权限、Diff、Stage、Commit、Archive、清理，并验证主工作区未被修改。每个 Fixture 的 `after` 钩子无论断言是否成功都会调用 `workflow.dispose()` 关闭 Server 与 SSE。

结果：通过，两轮均成功。

## 失败注入与恢复

- SSE 事件可能在 `prompt_async` HTTP 返回之后才被 Host 消费；E2E 等待可观察的 Permission/Attention 状态，不依赖传输时序。
- 初次 E2E 调试发现断言提前失败时 Fake Server 会保留 Node 句柄；增加 `OpenCodeAlphaWorkflow.dispose()` 并在 Fixture 兜底清理，随后测试进程可稳定退出。
- `emitSessionError` 验证失败投影；`holdQuestion` 验证等待输入；`holdPermission` 验证权限暂停；Dirty Archive 验证代码保留。

## 安全与数据边界

- 真实 Provider 测试仅本机运行，公开 CI 不需要凭据。
- Prompt 只在调用时传给 Runtime；Host Turn 仅持久化 `{ source: 'opencode', persistedText: false }`。
- Question 文本和回答不进入 Attention Payload；Fixture 事件用 `<sanitized>`。
- Git 不接受 Shell 字符串；所有路径先规范化并限制在绑定 Worktree。
- Renderer 不拥有文件、Git、Runtime 或凭据访问能力，只能调用固定 IPC。
- Runtime 输出、Diff、Attention 和 Native Event 继续按不可信数据处理并以 `textContent` 渲染。

## 已知边界

- Integration Worktree Merge、显式 Unstage 和完整 Git 原生面板属于 T4.4。
- Claude Adapter、Generic ACP 与跨平台入口属于后续任务池，不计入 Windows V1。
- 公开 CI 的文件修改由 Fake OpenCode 确定性产生；真实 DeepSeek 的网络请求与数据出口使用 T3.1 本机证据，不在公开仓库重放用户 Prompt 或输出。
