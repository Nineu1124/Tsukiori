# Tsukiori 24 周每日提交计划

制定日期：2026-09-21。审查起点：`d0f6ffe3efd9a4a5881f0e297f7ddfc6a94ac065`。

本计划按维护者的要求安排 **每天至少 1 个有实际内容的提交，包含周末**。从 **2026-09-21 到 2027-03-07**，连续 **24 周 / 168 天**，安排 **162 个日任务和 6 个阶段 Gate，共 168 个计划完成提交**。

具体日期、提交标题和验收条件见 **[每日提交日历](./daily-commit-calendar.md)**。日历是新任务完成状态的唯一清单；本文件定义执行规则与阶段标准。

目标是先修复已复现的可靠性问题，再把正式桌面入口的存储、后台任务、恢复与代码工作流接通，最后完善体验和发布准备。架构以[完整架构与实施方案](../../本地多Agent工作台_完整架构与实施方案.md)为准，执行遵循 [AGENTS.md](../../AGENTS.md)。新计划不改变历史 T0–T5/G0–G5 的编号与数量，也不把历史 Gate 当作正式产品链路已经接通的证明。

## 审查起点与计划可信度

[审查基线](../spikes/2026-09-21-review-baseline.md)记录了当前证据：

- 离线测试 297 项中 296 通过、1 项双 Runtime 恢复超时，单独重跑仍失败。

前 4 周围绕这些具体问题执行；第 5 周起是滚动工作量预算。每四周在 Gate 时重新评估下阶段范围、依赖与容量。日期安排是工作目标，不能代替技术验收；无法在当天完成的范围要提前拆小，并重排受影响日期。

## 每日提交规则

1. 按 Asia/Hong_Kong（UTC+8）的自然日执行，周末照常。建议每天保留一个固定工作时段，并在当天结束前完成验证、提交和推送；不伪造日期、不补空提交。
2. 同时只推进一个日任务。选取当天能独立完成、不会破坏既有行为的最小范围；若估算超出当天容量，先拆分计划，再开始实现。
3. 新任务编号为 `T-LT-D001` 至 `T-LT-D167` 中的 162 个日任务编号；第 28、56、84、112、140、168 天分别使用 `G-LT-01` 至 `G-LT-06`，所以日任务编号有相应空位。
4. 同阶段默认按日历顺序实施，依赖成立的独立任务可以调整；后阶段必须等待前阶段 Gate。调整时同时更新日历和报告，不越过验收。
5. 一个日任务或 Gate 对应一个完成提交，提交标题包含任务 ID。标题和正文用简洁中文，直接说明实际改动。例如 `修复(T-LT-D001): 保存失败时保留原状态文件`。
6. 缺陷修复与对应行为回归在同一个完成提交交付。测试任务应覆盖已经存在的行为或补验证工具；发现缺陷时先修复并更新当天范围，不能故意把新失败测试留在主分支。
7. 每日完成提交包含实现或实际文档产物、必要验证、证据报告、当天复选框。遵循仓库规则推送 `main`；推送失败先排除问题，再推进下一项。
8. 每周日检查下一周工作量；每四周执行一次 Gate。阶段中新增问题按严重性替换后续日期的任务，不无限叠加每日工作量。

“每天有提交”是实际产出的节奏要求。一次缺陷修复、一项边界测试、一份解决真实信息缺口的操作说明都可以成为提交；空提交、来回改格式、只修改日期不能算计划完成。

## 每个日任务的公共 Checkpoint

以下条件和日历中的当天验收条件必须全部满足：

- 明确实际用户场景、影响范围和正式调用路径；修复问题时有能暴露原问题的行为证据。
- 完成当天限定范围，执行与风险相称的验证。涉及持久化、进程、协议、安全边界时覆盖对应失败场景；未验证 Runtime 行为保持 `unknown`。
- 新的失败和既有失败分开报告。已知双 Runtime 基线失败允许无依赖的修复任务继续，但必须在 D022–D024 定位并解决，且 G-LT-01 通过前消除；不能隐藏或降低断言。
- 在 `docs/spikes/<任务 ID>-<topic>.md` 写明命令、版本、脱敏证据、失败和结论。纯文档任务的报告可以简短；架构决策另写 ADR。
- 更新当天复选框；执行 `npm run check`。涉及代码时增加相关模块验证，禁止把仓库检查通过等同于产品行为通过。
- 核对 diff 只包含当天范围；完成提交与推送。新引入的 CI 失败先修复或回滚，再继续后续任务。

低影响、可逆的文字和排版修改不需要编造测试。对协议与故障行为的验证不得绕过正式入口；外部 Provider 可以在离线回归中使用替身，真实账号验证的结果必须单独标注。

目前 `verify-checkpoints.mjs` 只验证历史架构清单。新日历在 D027 接入独立校验之前，需要人工或临时脚本检查日期连续性、ID 唯一性、依赖与勾选状态；现有 `npm run check` 不代表自动验证了这份日历。

## 每天的执行流程

| 时间点 | 需要做的事 | 当天产物 |
| --- | --- | --- |
| 开始前 | 看当天编号、前置条件、工作区状态和前次推送结果；确认范围能在当天闭环 | 明确的小任务与验证方法 |
| 实施时 | 只改当天范围；需要时先复现；遇到超出范围的问题登记后续任务 | 实现、必要回归或实际文档 |
| 收尾时 | 运行相关检查和 `npm run check`；写报告；核对 diff；更新复选框 | 一个可复查的完成提交 |
| 推送后 | 按仓库规则确认远端结果；有 CI 结果时处理新回归；简记下一步 | 已同步的提交与下一日入口 |

推荐验证命令按实际范围选择，不要求每个纯文档提交重跑全部产品测试：

```powershell
# 每个完成提交必须通过
npm run check

# TypeScript 或跨包行为发生变化时
pnpm run build
pnpm run typecheck

# 依具体改动选择，例如
pnpm run test:interactive
pnpm run test:database
pnpm run test:dual-runtime

# 提交前检查
git diff --check
git diff
git status --short
```

Gate 时执行对应阶段的组合回归。真实 Provider 测试仅在本地运行，记录版本和脱敏结果，公共 CI 不依赖个人凭据；安装、升级、长时间负载与真实服务验收不能用离线替身测试替代。

## 当天阻塞时如何维持节奏

每周预留 2–3 个已经确认价值、依赖成立的小任务作为候选备用，不提前制造问题。适合的范围包括：

- 已复现问题缺少的错误分类、诊断字段或有结论的复现报告。
- 现有稳定功能缺少的取消、空数据、配置冲突等边界回归。
- 与当前代码不一致、会误导用户的安装、恢复或故障排查说明。
- 已确认泄漏的订阅清理、已使用接口的类型补充、已有检查工具的遗漏。

替换时先在日历记录新的 `T-LT-B001` 等编号、日期、范围和验收，并注明原任务延期到哪里；完成后同样报告、检查、提交和推送。只提交没有结论的流水日志不算完成。

外部环境或网络故障可能影响当天推送。先保留已完成且已验证的本地提交，如实记录推送失败，并按 AGENTS.md 暂停下一顶层任务。不能把“计划每天提交”写成保证未来每天都会成功的自动执行结果。

## 每天交给 Codex 的任务模板

将编号替换成当天日历项：

```text
请执行 docs/roadmap/daily-commit-calendar.md 中的 T-LT-D001。
先读取 AGENTS.md、完整架构方案、长期计划和当天前置条件。
只完成这个日任务，按计划验收，补必要回归与脱敏报告。
若范围无法当天闭环，先拆成可独立完成的小任务并更新日历。
运行 npm run check 及相关验证，检查 diff，在同一提交更新当天复选框。
完成后按仓库规则提交并推送 main，报告实际结果。
不要跳到后续任务；遇到失败 Gate 或推送失败先处理阻断。
```

每日实施进度以日历复选框和对应验收报告为准；没有完成验证的任务和阶段 Gate 保持未勾选。
